# Cute: the guild dashboard

The in-game addon of <Cute>, the guild progging Forever's November release. Every member's client reads about a
hundred facts about its own character, plus what it meets in play (the bosses it kills, the instances it enters, its
factions, what it enchants) and the game's own statistics where the client reports them, shares them with the
guild over the game's addon channel, and shows the whole guild in one window. Officers decide per stat whether members
see each other's, and what they keep to themselves goes to them alone, never on the guild channel (Privacy and trust).
No server, no uploader.

Learned, not listed. Forever is an exploring game whose content is revealed over time, so the addon fixes no content
in code: what the guild meets in play is data each client finds, shares on the guild channel and keeps in the saved
variables (`CuteDB.known`), and the dashboard grows with it without a new version. Only the game's structure is fixed:
the equipment slots, the classes, the damage schools, the item class enums (a few ids stay where no documented call can
tell the thing apart; "Adding a stat" names them). 0.3.x listed Classic's content (Molten Core
and Onyxia attunements, Classic keys, world buffs, the raid factions, potions and flasks by Classic item id, raid
recipes, soul shards, totems, poisons) and a fixed set of enchantable slots that asked for head and shoulder enchants
Forever does not have yet and never for the neck enchants it does. All of that is gone in 0.4.0.

Nobody knows what is in the game at launch, so 0.5.0 ships what research and the beta showed as a seed (`Known.lua`,
generated: see The seed), checks it against the live client at login, and from there learns the rest by a fixed set
of rules (`Rules.lua`) that turn what the guild meets in play into knowledge. The Guide shows what they make of it.
We might log on at launch to an entirely different game: the seed is then thrown away and the rules run on the guild's
play alone. Design: `docs/superpowers/specs/2026-10-19-cute-known-and-rules-design.md`.

Cute starts with only the statistics. Every page is a module (`Modules.lua`, see Modules): the dashboard is the core
and always on; the Guide, and the module addons QuestBank's features come over as, are switched on per character in
Settings > Modules. Design: `docs/superpowers/specs/2026-10-19-cute-privacy-trust-modules-design.md`.

Design: `docs/superpowers/specs/2026-10-18-cute-guild-dashboard-design.md`. Plan: `docs/superpowers/plans/2026-10-18-cute-guild-dashboard.md`.

## Adding a stat

One line in `Stats.lua`:

```lua
D("fish", "Fish caught", "funny", { track = true, hint = "loot windows after a Fishing cast" })
D("gold", "Gold", "officer", { read = money, fmt = goldOf, on = "PLAYER_MONEY" })
```

`read` returns the value (under pcall; secret values read as nil), `count = "EVENT"` counts an event, `track = true`
is a value Sample.lua sets. `on` lists the events that re-read it; without it the heartbeat (every minute) does. `kind`
is int, flag, text, list (bitmap over `of`) or pips. `fmt` formats the cell (hours, percent, gold from copper).
`slow = true` marks a stat that changes every few seconds (time played, XP into the level): it travels on Comm's
two-minute flush, not as it ticks. `default = "self"` keeps it to the officers unless they open it: whispered to them,
never on the guild channel. Every stat the officers can set has a code for life in `S.CODES`, two letters, the short
name Guild Info's line and the policy call it by (Privacy and trust): a new stat takes one nobody has had, and a stat
taken out leaves its code in `S.RETIRED`, never given again (a client holding an older policy would read it as the new
stat's); a module's stat without one goes by `_` and its id. `reveals` names the stats (or categories, `gc_bosses`) a member could work out exactly from
this one's value with what else the guild sees, and the stat goes the strictest way of its own and theirs; `counts`, on
a stat made of others (Ready), names the ones it may count, each only while everyone may see it (Privacy and trust: No
Everyone value rebuilds an Only-you one); the harness fails on a stat that goes to the guild while one it reveals does
not. `lo` and `hi` bound what a member's value may be (0 to 2^31 unless given) and `grows` marks
a lifetime count the addon keeps, which never goes down (Privacy and trust). `gear = true`
or `bag = true` reads it again with the gear or the bags 2 s and 10 s after every loading screen. A stat names no
content of the game that the game can tell it: what Forever has is learned in play (below). A few ids stay fixed,
each where no documented call tells the thing apart, and each named where it is used: the Healthstones by item id
(Forever's own item list, `plan/items-db.json`; a mana gem is the same item class and subclass), the Hearthstone spell
(8690, for hearths and wasted hearths), the skill line ids of the primary professions, Fishing, Cooking and First Aid,
the five Legacy perks by trait node, Forever's PvP rank track (Major Faction 2800), and the Legacy ids
`Constants.LegacyConsts` gives (its documented values the fallback). Hours to 60 runs over the XP curve the guild
learns (Rules.lua rule 6); 0.4.0's Classic table is gone. A Fishing cast is known by
name (`C_Spell.GetSpellName` of the spell is the Fishing skill line's name), not by Classic's four rank ids.

A `read` may only call what Forever's generated API docs list (`research/wow-ui-source-forever/.../Blizzard_APIDocumentationGenerated`),
what QuestBank reads on this client (`GetInventoryItemLink`, the taxi nodes) or what Blizzard's own Camelot UI code
calls. The globals no doc lists are read on that last ground: `GetInventoryItemID` and `GetInventoryItemQuality`
(Forever's own character sheet, `Camelot/PaperDollFrame.lua` `PaperDollItemSlotButton_Update`),
`GetInventoryItemDurability` and `GetInventoryItemCount`
(Camelot's equipment flyout reaches them through `EquipmentManager_GetItemInfoByLocation`), `GetNumUnspentTalents`
(the mainline `TalentFrameBase.lua` the camelot game type loads), `GetCategoryList`, `GetCategoryInfo`,
`GetCategoryNumAchievements` and `GetAchievementInfo` (Blizzard_LegacySystem, Forever's achievement window, which loads
on camelot), `GetTotalAchievementPoints` (Blizzard_Communities, whose toc limits no game type), and `GetNumLootItems`,
`GetLootSlotInfo` and `GetLootSlotLink` (Forever's loot frame, `Mainline/LootFrame.lua`, which the toc loads for every
game type; read for a boss's loot, never looted from: `LootSlot` is never called). Three more are in the
same binary but called only by the mainline achievement panel, which camelot never loads: `GetStatisticsCategoryList`,
`GetStatistic` and `GetLatestCompletedAchievements`. Cute probes for them at login (`C.Callable`) and reads them only
where they exist. The harness mocks the documented set, the QuestBank set and every undocumented one, each named in
its `UNDOCUMENTED` table with its evidence, the three probed ones for `withStats` clients only, so every scenario runs
with and without them; a mock without an entry there is refused, and the first scenario fails on any stat that reads
nil. `/cute api` prints how many statistics this client defined (or why none) and which of the undocumented functions
it has (`DoEmote` and the never-mocked `GetAverageItemLevel` included), lines to paste; a stat that reads a missing one
shows "?" with "X is missing on this client" in its tooltip, on the Me page and under `/cute errors`. Pass a global to
`Get` and `Num` by name (`Num("UnitLevel", "player")`) so that holds for it too. Gold stats keep copper and show gold.
Role and raid spec are per character; the main is account-wide.

### Gear

The gear stats read your slots the way Forever's character sheet does: `GetInventoryItemID` says what is in a slot,
`GetInventoryItemQuality` its quality, the item level comes from the id (`C_Item.GetDetailedItemLevelInfo`, whose
ItemInfo argument takes an id; `C_Item.GetItemInfo`'s fourth return where an uncached item reads nothing there), and the
item level is the average over the worn slots whose level reads. The link is read for the enchant alone and only when
it is a plain string. One scan of the slots serves every gear stat read in the same frame.

They refresh without a reload. 0.3.1's gear stats listened to `PLAYER_EQUIPMENT_CHANGED` alone, and the window learns
of a value of yours only when a read changes it. At login the inventory can arrive after the loading screen, with
`UNIT_INVENTORY_CHANGED` and no `PLAYER_EQUIPMENT_CHANGED`; an enchant changes an item's link and fires only
`UNIT_INVENTORY_CHANGED` too. So nothing read the slots again until the heartbeat, five minutes on: the owner had to
reload. (0.3.0's "15 of 17 slots empty, item level ?" on a character in full gear looks the same.) Forever's own
character sheet refreshes a slot on `UNIT_INVENTORY_CHANGED` for the player
(`Blizzard_UIPanels_Game/Camelot/PaperDollFrame.lua:2055-2063`). Now every gear and bag stat listens to
`PLAYER_EQUIPMENT_CHANGED`, `UNIT_INVENTORY_CHANGED` (yours only: `RegisterUnitEvent`, and a unit check for a client
without it; where `RegisterUnitEvent` fails, every unit's with the same check) and `GET_ITEM_INFO_RECEIVED` (only for
an item the last gear or bag scan met: a chat link, another addon or the Legacy window asks the client about items all
the time, and each would have scanned the slots and the bags again); the gear and the bags are read afresh 2 s and
10 s after every `PLAYER_ENTERING_WORLD`; the heartbeat runs every minute, not five (Comm still sends only what
changed, so a quiet minute sends nothing). On a table page your row, the first, is filled again in place when one of
its cells changes.

### Enchants: learned per slot and kind of item, the seed beside it

No slot is fixed in the code as enchantable: the guild learns what takes an enchant, and the seed (`Known.lua`) says
what research found Forever has. Each client reads, per worn slot, whether the item's link carries a permanent
enchant (its second field) and the item's kind as the game classes it, `class.subclass` from
`C_Item.GetItemInfoInstant`'s sixth and seventh returns (`C_Item.GetItemInfo`'s twelfth and thirteenth for an item the
client's data lacks): a bow is 2.2, a gun 2.3, a wand 2.19, a shield 4.6, a book held in the off hand 4.0. It sends
`enchanted` (a list over the slots; no column) and, beside it, `ench_kinds`, a hidden text stat
(`"2:4.0:2564 18:2.2:30"`, the slot, kind and enchant of each enchanted item; a 0.4.0 client reads the slot and kind
and stops at the second colon; in the full record after the GUID, and as a delta when it changes). The guild's
knowledge is per slot and kind: `CuteDB.known.enchant[slot] = { n, at, who, kinds = { [kind] = { n, at, who } }, ench
= { [id] = { n, at, who } } }`, built from your own read, from every member record that arrives with its GUID
(`Roster:Apply`) and from the records already saved, counting each member once by GUID (a delta that comes before any
full record has brought the GUID teaches nothing yet, so a member is never counted under a sender string and again
under the GUID). It is kept apart from the records, so it survives a /reload, the roster's pruning and the member
leaving. Enchanted slots goes the way of Missing enchants and Empty slots (with the slots the guild knows take an
enchant, the ones it leaves out are missing or empty), and its kinds with it, so with the defaults only the officers'
clients hear the members' enchants and learn from them; each says what it learned, the slots and the kinds of item,
in the officers' word (`1N`, Privacy and trust), which a member's client takes as its own knowledge, "from the
officers". A kind of item in a slot counts as learned once two members at least were seen with an enchant on it (by
GUID, your own read one of them, a member the officers marked untrusted none): one edited addon claiming an enchant
asks nobody for one, and the first member's is kept, waiting for the second (Privacy and trust).

Missing enchants (`unenchanted`, its id kept) is the worn items without an enchant where the guild has learned the same
kind of item enchanted in that slot, or, for a character at the rules' enchant level (`enchantDoubtLevel`, 30 unless
the officers set another), where the seed has an enchant for that slot and kind (Rules.lua rule 5: only once Rule 0
has found the seed fresh, and not for a slot whose recipes the client lacks or that the guild has doubted). A
character levelling through gear it outgrows in a few levels is asked only for what the guild has actually enchanted;
the Guide gives the seed's slots to it as advice. The seed is a prior beside `CuteDB.known.enchant`, never copied into
it, so what the guild learned stays the guild's. A slot alone says too little: Forever has scopes (Crude, Accurate,
Deadly) and shield enchants, so one hunter's scoped bow would ask every wand for a scope, and a tank's enchanted
shield every caster's off-hand book, neither of which can have one. So a wand, a gun nobody has scoped and the seed
has no scope for, and a book in the off hand where only shields take one are never asked for; an unscoped bow is once
scoped ones are seen. A head or shoulder enchant, which Forever has none of yet, is asked for only once members wear
one. Where a worn slot that takes an enchant gives no readable link, or an unenchanted item's kind does not read yet,
it reads nil with that reason in its tooltip. A new slot or kind learned, a threshold retuned and a level up ask your
own Missing enchants again, so members show it on their next read and the officers on receipt. An item whose kind
reads and takes no enchant in its slot is never asked for, link or none. The tooltip names each missing slot, with
the kind on your own row ("Ranged (Bows)"), and on how many members the guild has seen one there (or "from research"
or "seen in the beta", where only the seed says so): seen, since the count never falls as members leave or change
their gear. A member's list is the one their own client worked out, by their level, shown through this client's
knowledge, so an older client's head and shoulder never appear. The cell shows the count alone.

### Consumables, reagents, buffs

Potions, elixirs, flasks, food and drink and bandages are counted by the game's own item classes
(`Enum.ItemClass.Consumable` and `Enum.ItemConsumableSubclass`, looked up by name with the documented values as the
fallback) from one cached scan of the backpack and the four bags (`C_Container.GetContainerNumSlots` and
`GetContainerItemInfo`, `C_Item.GetItemInfoInstant`, and `C_Item.GetItemInfo`'s class and subclass for an item the
client's own data lacks), so whatever potion Forever adds counts the day it drops. Healthstones stay by item id: they
are the one class reagent with evidence on Forever (QuestBank's uploads find Minor and Lesser Healthstones in Forever
characters' bags), and no documented call tells one from a mana gem, the same class and subclass. The ids are Forever's
own item list (`plan/items-db.json`, beta build 1.60.1.70291): 5512, 5511, 5509, 5510 and 9421, Minor to Major, and the
improved ranks a talented warlock conjures, 19004 to 19013. Soul shards, shaman totems and rogue poisons had no
evidence and are gone. Readiness (`ready`) weighs the gaps everyone may see of four: an empty slot, a missing enchant
(as Missing enchants counts them, above), durability under 50%, no potions. With the defaults the officers keep the
first two, so it counts durability and potions: ready with no gap, gaps with half the ones it counts or fewer, no with
more. Its tooltip names the gaps and what it counts; an officer sees the others in their own columns.

Raid buffs missing is learned too. A buff of five minutes or more that a guild mate (`UnitIsInMyGuild` of the aura's
`sourceUnit`, not you) cast on you is remembered by name (`CuteDB.known.buffs`: when, the GUIDs of the guild mates who
cast it, how many times it came on). Remembered is not yet a raid buff: one counts once two different guild mates have
cast it on you, or one has on three separate occasions (an occasion is the buff coming on while it was not; that is
kept in the saved variables, so a /reload is none), and one no guild mate has cast on you for two weeks is forgotten.
The stat counts the raid buffs you have not got, and only in a group or an instance (`UnitExists("party1")`,
`UnitInRaid("player")`, `IsInInstance`); alone outside one it is 0, and your own tooltip says so. So a Soulstone, a
Thorns or a Water Walking while leveling is no raid buff, and nothing is missing while you quest alone. Your own
tooltip names each missing one, from how many guild mates and how many times. (QuestBank's uploads show four of
0.3.x's six on Forever characters, Fortitude, Mark of the Wild, Arcane Intellect and Kings, and none of Divine Spirit
or Shadow Protection: a list would have been wrong either way.)

### Discovered: bosses, instances, factions

Three kinds of stat are defined at run time, like the game's statistics, the first time a label for one is known (from
your own play, or from the guild channel once a member's value for it has come or two members agree on it), and kept
by every receiver as ints whether or not it has defined them; the 1000-a-member cap covers them and the statistics
together:

- `e<encounterID>`: kills of that boss by this character: `ENCOUNTER_END` with success 1, or `BOSS_KILL` where no
  `ENCOUNTER_END` for the same encounter came within five seconds either side, never both. The first kill's time stays
  in your own saved variables. Labelled with the encounter's name, grouped by the instance it was killed in
  (`GetInstanceInfo` at the kill: its name and instanceID). Outside an instance that is the continent, "Eastern
  Kingdoms" (0) or "Kalimdor" (1), so a world boss is filed under its continent, not its zone: a zone has no instance
  id of its own, and zones sharing the continent's would rename it with every kill. Each kill is also claimed with the
  group it was killed in (`1K`, rule 9), which the rules learn from only where a group mate names it back.
- `i<instanceID>`: times this character entered that instance: a new entry when the instance differs from the last
  one this character was in, or on the first loading screen of a login (the character left the world); the last one
  is kept across loading screens, so a run back after a wipe is no entry, and a /reload never is one. Labelled with
  the instance's name, a dungeon or a raid as `GetInstanceInfo`'s instanceType says. The summary ints fold into this,
and go with their categories (Privacy and trust):
  Dungeons run and Raids attended are entries into party and raid instances, Raids this week the same since Monday,
  Bosses killed the different bosses killed, Dungeons seen the different dungeons entered.
- `k<encounterID>`: the level this character was at its first kill of that boss. No stat (nothing shows it), kept per
  character with the counters, sent with the boss kills (a delta at the kill, the discoveries pass after); a receiver
  keeps it as an int in the member's record, where the rules learn a dungeon's level range from it. A 0.4.0 client
  drops it. (The design offered the label pass for it; the record is the cheaper correct place: the level is per
  member, a record is joined by GUID, saved and pruned with its member, where a label is kept once per id and the
  labels message carries no GUID.)
- `f<factionID>`: this character's standing (`currentStanding`) with every faction its reputation list holds, the rows
  with a standing and the headers with rep (`C_Reputation.GetNumFactions` and `GetFactionDataByIndex`), read again on
  `UPDATE_FACTION` at most once a second; a faction listed before is asked by id (`GetFactionDataByID`) while its
  header is folded. Shown by its reaction (`FACTION_STANDING_LABEL1..8`, the number where the client has none): yours
  as your list gives it, a member's from the standing ranges your own list showed (`CuteDB.known.reactions`).

The labels travel in their own message, `1L|key=label;...` (`e<id>:<instanceID>` for a boss and its instance,
`i<id>:<p|r|w>` for an instance and its kind, `w` the continent of an open-world boss, `f<id>` for a faction, and
`l<encounterID>=<item>.<item>...` for the items this character saw in that boss's loot window, in base 36: rule 8; a
0.4.0 client skips the key), for a
new discovery a second after it and in a
labels pass after the statistics pass, at the hello (only what this session has not sent) and in answer to an ask
(all), each pass the ids of the sender's own record, every boss with its instance, chunked to 255 bytes. A label is
UTF-8: bytes over 127 are kept (an accented name, a German client's dungeon), `|`, `;`, `=` and control characters go,
a broken sequence goes, and it is cut at 60 bytes without splitting a character. A label is its sender's word, kept
by the sender's GUID (`CuteDB.known.voice`, four voices an id, 500 ids a member; none from a member the officers
marked untrusted, nor from a sender the roster has no GUID for, nor, on a member's client, of a category the officers
keep: a label says who met the thing). A receiver keeps the first one's in `CuteDB.known.labels` (with the instance of
each boss), unless the seed names it, whose name and instance stand until two members agree on another (`S.LabelOf`),
and defines the stat once a member's value for it has come or
two members agree on it, so a member who never met a boss shows it under its instance with the guild's values already
kept; a label the client found itself is never replaced by another's, and two members who agree replace a first one
that differs. What a label decides needs two who agree, or your own play (`S.Sure`): an instance's kind (where its
entries travel: one member's word on a kind is unsure, and the entries go the stricter of Dungeons and Raids; the
seed's kind for an instance it names), the instance an awaited dungeon is, a name over the seed's, a seeded faction
met. Your own discoveries always define their stats; the channel's define a thousand at most, four hundred first
named by one member (each charged to the member whose value or word defines it, else another who named it), so one
edited copy's junk labels keep none of yours out. A label tells who met the thing, so it goes the way its stat's value does: a category
the officers keep to themselves has its labels whispered to them. At login a 300-statistic, 40-boss, 18-instance,

### Who is who

Forever names a character with two words ("Helga Bluntforce"). On camelot `UnitName`'s second return is the surname,
not a realm (`Blizzard_FrameXMLUtil/Camelot/NameUtil.lua`, which loads on camelot only, joins the two with
`Constants.CharacterNameSeparatorConsts.CHARACTERNAME_SURNAME_SEPARATOR`); the guild roster lists both words; the
channel names a sender its own way; and `ClubMemberInfo.name` "may be encoded as a Kstring", a `|K...|k` escape the
font draws as the name, never compared with `==`. And the game hands a guild addon message back to its sender too.
0.3.0 keyed you by a name it built from `UnitFullName` ("Helga" and its second return) and the roster by its names
with a realm added, so it showed the owner three times: "Helga (you)", "Helga Bluntforce (no addon)" from the roster,
and a grey "Helga Bluntforce" of question marks: her own messages come back under the channel's name for her, which
matched neither, kept as a member's record. The roster's prune dropped that record every two refreshes, as a name not
in the guild, and her next message made it again with that message's ids alone (a statistics delta carries none of
the columns), hence the question marks.

So no name is a key. A roster member is its GUID, else its club member id; you are the member marked `isSelf`
(NeverSecret) or carrying your GUID. Records stay under the sender string the channel gives, and every full record
starts with the sender's GUID (`guid`, a hidden text stat: in `Stats.byId`, not in the list, so no page, column,
checklist, policy pair or the web page shows it; `ench_kinds`, above, is the other), as does the ask
(`1R|guid|stamp|word|fp`, Privacy and trust; 0.5.x's `1R|guid` and a bare 0.3.0 `1R` are still answered).
A receiver joins a record to the member with the same GUID, by name (below) only while no GUID has come with it, and
folds two records of one GUID into one. Whether a message is your own, handed back, goes the same way (`Roster:FromMe`): the GUID decides wherever
the message (a full record, an ask) or the record under its sender carries one, so a namesake's record is never taken
for yours by its name; a delta or a policy, which carry none, count as yours under a sender string your GUID came
under, else by your names. Your own is dropped and its sender remembered as you for the session. A GUID is taken
only where the roster bears it out (`Roster:Vouch`): where the sender string, the channel's, names one member (below),
a GUID that member does not have was never the sender's, and nor is one whose member has another first name. It is
dropped and the record marked suspect (Privacy and trust); the message counts as the sender string's, and is yours only under the sender string the
roster names you by. A record keeps the GUID it came with unless the roster names its sender by another, and is folded
into another sender's record only then. What came before the roster was known is judged the first time it is. The
hello is said only in a guild: a character that joins one after login says it then, its ask first, before any delta
goes out (the ghost row would come back otherwise). `Rows()` gives you exactly one row, the first, named as the roster
names you; ranks and the officers' check go by the member the sender string names, never by a GUID, and a policy you
set is marked yours rather than matched by name. `C.Me()` stays 0.3.0's key for your saved counters (`CuteDB.chars`),
so nothing moves, and is read once a session (the first non-nil key), so a second return that reads one way early and
another later cannot save a choice under one key and read it under another. Your emote lines count by the event's GUID. A value the client may make secret is asked `issecretvalue` (or made plain) before anything compares
it, `nil` included.
Records are kept for up to a thousand members, a guild's most (0.3.0 kept two hundred).

## Privacy and trust

Design: `docs/superpowers/specs/2026-10-19-cute-privacy-trust-modules-design.md`, sections 1 and 2.

**Only-you is routing, not hiding.** Up to 0.5.0 an Only-you value travelled on the guild channel like every other and
was hidden in members' windows: any addon listening to the prefix, or the saved-variables file, had it. Encryption
would not help (any key ships inside the addon). Now a value the officers keep to themselves (`Policy:Route`: a stat by
its visibility and that of what it would reveal, below, a hidden one by the stat it travels with, a kill level by its boss, a discovered id this client has not
defined by its category) never goes on GUILD. Each client whispers it, in the same messages (`1D`, `1F`, `1L`, `1K`),
to each officer online: `C_ChatInfo.SendAddonMessage(prefix, msg, "WHISPER", target)` (documented on this client), the
officers taken from the sender's own C_Club roster (rank order against the policy's threshold, online by presence)
and each named by the sender string their own Cute's full record came under on the guild channel, the name the game
takes for a whisper (a roster name may be a Kstring, which is none), and only a sender string the roster names that
officer by. An officer still on 0.5.x is none (its record says its version: 0.5.x drops every whisper), so what it
would lose waits for it to update and ask. An officer
whose Cute has not spoken yet gets them in the answer to their ask (`1R`): every client notes the officers among those
who ask, by the sender string, and whispers them the Only-you part of its record with its answer, and the statistics
and discoveries kept to the officers with the statistics pass's answer. The roster gives every member the officers'
GUIDs, so a GUID in a message proves nothing: an ask or a full record carrying an officer's GUID from a member's
sender string is a member's, gets nothing whispered, and marks its sender suspect.
An officer heard from for the first time after your hello (you logged in after them) is told once, two seconds on; a
member made an officer during the session (a promotion, the officers' threshold raised) asks again at once, and every
client whose roster now names them an officer, having heard them as a member, tells them too, the statistics and
discoveries kept to the officers with it, whichever roster saw the promotion first (an ask a roster that still named
them a member answered was a member's, and whispered nothing); so what does not change reaches them, and an officer no
more who is made one again is told again. A whisper is taken only
of those four kinds and only from a sender string this client has heard on the guild channel (its record says so:
only a guild message makes a record), the roster naming a member by it, carrying the GUID that record has where it
carries one; a whisper never makes a record, sets or changes a GUID, or folds two records into one. The game delivers
a whisper from anyone and a guild message only from the guild, so someone outside it whispering under a name like an
officer's (a sender string and a roster name are matched loosely: Who is who) is ignored and whispered nothing.
Whispers that come before the roster is known (an officer's client at login, its roster slow) are kept in memory and
judged once it is, and so are the records and deltas the guild channel brings meanwhile (a record made before the
roster listed anyone decided whose guild 0.5.x's saved variables were by what this session heard, not by what was
saved). A member's client never receives another member's
Only-you values, so there is nothing to bypass, and drops any that come all the same (from an edited copy). The labels
and kill claims of a category the officers keep go their values' way: a label says who met the thing; one held back as
it leaves (the policy closed its category meanwhile) goes to the officers at once.

When the officers open a stat to Everyone, every client sends its value on the guild channel at once and from then
on (`Comm:Opened`, a discovery's label and a boss's claims with it, which went to the officers alone while it was
closed); when they close one, members' clients delete the values they hold for others as the policy arrives
(`Policy:Purge`, only when the policy closed something it did not before: the policy a client holds, taken again at
every member's login, deletes nothing and costs nothing). The saved records on a member's client hold no other member's
Only-you values once 0.6.0 has run: the purge runs at login, once the roster lists the character with its rank, this
client holds the policy Guild Info names (below: a threshold the officers changed while you were away is not taken for
theirs) and the saved labels and statistics are defined (so every value's route is known; a statistic the client's
probe may still define waits for its last word), and again when the roster says it is an officer no longer. A roster
read that does not list you, or lists you with no rank, says nothing either way (an officer at the last read that said
is one still for the whispers that come while a read lists her without a rank, a blip of the roster mid-session: kept,
not dropped, and a value her client dropped all the same is asked for again at the next read that lists her, whatever
the roster said of her meanwhile; 0.6.0's first builds dropped the whispers of those seconds and asked for nothing), nor
does one that does not list a character of the account an officer at its last login, or lists it with no rank (`Roster:AccountOfficer` says unknown,
and a member alt's first purge waits for a read that says; two complete reads half a minute apart that still lack the
character say it is no character of this guild, as a record is pruned, and the file is purged then. 0.6.0's first
builds took one such read as "no officer", and a slow roster at an alt's login deleted the officer's held Only-you
values). The saved variables are the account's,
though (`## SavedVariables`), and an officer's alt is often a member: where the roster ranks another character of the
account an officer of this guild now, the file is that officer's. A character is known by its GUID, kept with its last
login (`CuteDB.chars[..].guid` and `officerOf`, the guild's club), never by its name: a namesake officer of the guild
vouches for no alt of another realm or surname (0.6.0's first builds matched the account's characters to the roster by
first name, and such an alt kept the members' Only-you values unpurged). One whose GUID the roster does not list is no
character of this guild; one saved without a GUID goes by its last login, and in a file 0.5.x saved by having set the
policy, where the roster names one member of that name an officer now: a setter the roster cannot name (renamed, or
gone from the guild) vouches for nothing, and the file is purged once (0.6.0's first builds kept it for good: a member
alt's file held the members' Only-you values session after session). That costs the officer of a renamed 0.5.x
character nothing they cannot have again: their next login asks, and every client whispers them what went. Where the file is an officer's, and a member character
of the account deletes nothing of it (its window shows none of it all the same: `Policy:CanSee`). An officer demoted
while offline is no officer by the roster, so the next login of any character of the account purges the file (0.6.0's
first builds believed that character's last login over the roster, and kept the members' Only-you values through every
alt's login). Never on a character's own word: the roster reads its rank, so an officer demoted after their own last
change purges like any member (0.6.0's first builds took any policy this account set for an officer's file, and never
purged), and a change of who sees what they made and did not save counts only while the line's officer ranks name
them an officer: demoted, the change gives way to the line, so neither a stat it opened nor ranks it raised keep the
members' Only-you values on their client (0.6.0's first builds kept both, across relogins). An
officer no more, in the session or since their last login, also drops every member's Ready their client holds: an
officer's client is never purged, so a Ready it kept may count a gap the officers closed meanwhile, and each member's
next read says it again. A character that leaves the guild, or is removed from it, keeps what its file held. An
account's characters may be in different guilds: each guild's policy and its members' records are kept by the guild's
club (`Policy:ForClub`, `CuteDB.policies`), so another guild's roster prunes and its policy purges none of this guild's
records (0.6.0's first builds kept one roster for the account: an officer's alt in a second guild deleted the
officer's records within a minute); what the guild learned (`CuteDB.known`) is the account's first guild's
(`CuteDB.knownClub`), and another guild's policy takes out of it only the traces of the members its own roster lists.
The records and policy 0.5.x saved say no guild: they are the guild's whose roster lists a member one of the records
carries (`Policy:Adopt`, before anything prunes, reads or learns from them), judged by what was saved alone: what the
guild channel brings before the roster lists anyone waits for it (above), so a slow roster neither keeps a parked file
from its guild nor hands a second guild the first's. Where the account's first 0.6.0 login is
in another guild they are put aside (`CuteDB.policies["?"]`), that guild starts with none, and the first guild whose
roster lists them takes them while it has no records of its own (0.6.0's first builds gave them to whichever guild came
first: an alt's login in a second guild pruned the main guild's records and took its policy).
Each character reads its own guild's Guild Info, so another guild's line routes nothing here.
Cost: one more copy of each Only-you delta per officer online. With three officers online each client sends 14
messages in its first minute, the officer who says the officers' word (below) 15 (the harness measures it, a member
with 300 statistics among them);
what stays true, and the page says so: an officer's client holds members' Only-you values, and its saved file contains
them.

The copies never hold up the guild's deltas. Comm sends one message a second. 0.6.0's first build queued each
second's changes as a delta on GUILD and a whisper per officer and dropped only copies of the same text, so with four
officers online and gold changing every second it fell 175 messages behind in a minute, the guild's deltas waiting
behind the whispers. Now a delta to a way (the guild channel, or one officer) that has deltas waiting goes into them:
a newer value of an id takes the older one's place in the delta that holds it, a new id joins the first with room, and
each keeps its turn; only what fits in none goes as a message of its own, and every value message still waiting behind
the one a value went into (a later delta, a record's chunk) gives that id up, so an older value never arrives after a
newer one (a lifetime count would seem to go down and mark an honest member), and a value that changes every second
waits in one message even behind a full one. The policy goes first (the ask, an answer with one, an officer's
broadcast), so a client waiting for the policy Guild Info names has it however much the answerer has queued; then the
guild's messages ahead of the whispers; a whisper that has waited ten seconds (`FAIR`) goes in its turn, so a guild
channel busy every second still lets the officers hear. The harness
measures a minute of gold every second and deaths every third with four officers online: the queue holds five at most
(the guild's and one per officer), no guild delta waits behind a whisper, every officer ends with the last gold; and
twenty seconds of deaths every second too: no whisper waits more than 13 s.

**The policy lives in Guild Info.** 0.6.0's first build routed by the policy each client last had from an officer, so a
member who was offline when the officers closed a stat sent it on GUILD at login, and all session where no officer was
online; three rounds of review then kept finding timing gaps in members passing the officers' policy on to each other
(relays, a hold at login, stale officers ending it, a second guild, alts). Now the policy is where the server keeps it
and only the officers can change it: one line at the end of the guild's Guild Info text.

- The line: `Cute 1 <stamp> <ranks> <fingerprint> <what differs>`, for example
  `Cute 1 tn8280 1 f8f61866ed7ec926 -de-en-zo`: the format, when it was saved (base 36), the officer ranks, the
  policy's fingerprint (two 32-bit FNV-1a hashes of "ranks:what differs", forwards and backwards, 16 hex digits:
  `Policy.Fingerprint`) and what differs from the defaults, a token per stat or category, `+` Everyone and `-` Only you
  before its code (`Stats.lua` `S.CODES`: two letters for life; a discovered category's in `S.FOUND`; a statistics
  category by its number), in the order of their codes byte by byte (a string's `<` goes by the client's locale, which
  a Norwegian client need not share). Guild Info takes 499 letters (the game's own editor's limit in
  `Blizzard_Communities/GuildInfo.lua`; counted here in bytes, which a letter never has fewer of): where the guild's own
  text leaves no room for the whole line, nothing is saved, and Settings say how many bytes fewer it needs (and count
  Guild Info in bytes: a letter such as æ takes two). 0.6.0's
  first builds then saved the fingerprint alone and took the policy from any member's copy that matched it; a 64-bit
  hash is no signature, and an edited copy with an evening of work could have made one match, so that path is gone: a
  line whose text does not match its fingerprint is one nobody can read (an officer saves it again). Only the line's
  shape is Cute's: a line of the guild's own that starts with "Cute" is the guild's.
- Saving: an officer's change in Settings (Who sees what: a pair, the officer ranks, Reset to defaults) routes on that
  officer's own client, and Settings shows Save to Guild Info with the line's length (the line itself in the button's
  tooltip). The click calls `C_GuildInfo.SetInfoText` (documented) with the guild's text as it is and Cute's line at its
  end in place of the one there, then sends the policy on the guild channel, so the clients online stop sending and
  read Guild Info again at once (Reading, below) rather than at their next minute's roster read. Saving needs a rank allowed to edit Guild Info (`CanEditGuildInfo`, which Blizzard's own
  Guild Info panel asks, `Blizzard_Communities/GuildInfo.lua:53`): for an officer without one the button is greyed,
  Settings say why, and the change stays on that officer's client (the policy an officer sends carries the line's
  routing while a change is not saved, so it never goes on the wire). A line another officer saves meanwhile replaces
  an unsaved change, and so do the line's officer ranks where they no longer include the officer's; a line a newer Cute
  wrote is not written over (update first). Nor while this client waits for Guild Info to be read again (another
  officer's newer policy heard, stricter than the line or not, or its own save not read back yet), nor where the text
  the game holds now has another Cute line than the one this client routes by: Settings say to wait a moment (0.6.0's
  first builds saved over a line another officer had saved seconds before, and a stat that officer closed opened again
  with nobody told; a second officer holding the game's copy from before and a change not saved, who had heard the
  first's policy, saved over it two seconds on where that policy was no stricter than the line, which raises no doubt;
  and a second save of one's own within those seconds was judged by the first, so the game's copy from before reverted
  both and said the game had not taken them). An officer's policy heard that is newer than the line and not its, from
  an officer the roster names one, refuses Save until a read confirms the line (another line, or the one held eleven
  seconds after an ask made since, as a line waited for is judged), kept with the guild across a /reload. Two saves in
  one second, before either officer heard the other, cannot be told apart in time: the second stands, and the first
  officer hears at her read-back that another officer saved over her save; her change is made again on the line read,

- Officers can mark a member untrusted: on the Officers page a click on a row picks the member and Mark untrusted
  (Trust again) sets it, sent with the policy (`u=<GUID>`) a few seconds on. An untrusted member is left out of
  every rule's evidence (enchants, kills, ranges, XP, loot, claims) and of the rankings (the Hall of Shame's cards,
  the Statistics page's leaders and rankings); the tables still list them, marked "(untrusted)" for the officers.

What one member alone can still do: send labels, the names of what they met, which fill gaps nothing else has named
(the client's own names win, two members who agree replace them, and they decide nothing: an instance's kind, an
awaited dungeon's place, a name over the seed's, a faction met all take two; a thousand junk labels define no stat and
keep none of yours out), a boss's loot for a boss the guild has a name (the seed's included) or a witnessed kill for
(forty items a boss, twenty-four of them brought by one member alone, an item from your own window or from a member
holding fewer taking the place of the oldest of the one holding the most; six hundred bosses from the channel, two
hundred first from one member), kill claims (four hundred a session, the oldest out), asks (one a sender in three
minutes starts an answer, the statistics pass once in half an hour a member; the policy once in thirty seconds an
asker while what this client would answer with is the same, so a copy asking every second got it thirty times a
minute and now twice; an officer's ask always gets what the officers keep, whispered, and the guild's part on the same
terms as a member's; an untrusted member's ask gets the officers' policy alone, once in five minutes), policies (a
member's routes nothing and asks nobody's client for the roster), and their own values within the bounds. Nothing
an untrusted member said names anything: a name only they gave (a boss's, an instance's, its kind) is none, what
they said before the mark included, and their records' values define no discovered stat at the next login. Knowledge learned before 0.6.0 came from single
voices and uncorroborated kills; what the rules rebuild (ranges, doubts, new dungeons and bosses, a boss's loot) now
waits for the guild's corroborated play, while who saw a dungeon or a boss carries over as before.

## Modules

Cute's core is the shell: the window and its tabs, the flat skin, Settings, the guild channel, the roster, the policy,
the stats registry and the knowledge model. Every page registers itself with the core (`Modules.lua`), and the tabs
and Settings' sections are drawn from that list, in each module's order:

```lua
C:RegisterModule({
  id = "guide", title = "Guide", order = 20, builtin = true, default = false,
  page = function(ui, scroll) ... end,     -- draws into the shared scroll area and the band
  settings = function(ui, column) ... end, -- its own Settings section, drawn with the column Settings hands it
  stats = function(D) ... end,             -- registry entries, D as S.def
  events = { PLAYER_LEVEL_UP = fn },       -- heard while it is on
  officer = false,                         -- officer ranks only: no tab and no section for members
})
```

A page draws with the window's pieces (`UI.Button`, `UI.Check`, `UI.Text`, `UI.FitText`, `UI.Flat` for a flat
texture, the pools and virtual lists, a list of its own by key with `ui:List(key, make)` on `ui:MakeLine`'s row, which
a page that does not fill it has cleared like the window's own, the band's `ui.bandLines`, `ui:SetBand`), and a section with the column (`Head`, `Note`, `Check`, `Choice`, `Edit`, `Step`, `Rule`, `Buttons`,
`Broadcast`), which sets the spacing, so a module looks like Cute. A box's edge is a mid grey, 3:1 on the panels
(`build.py` checks it with the page's), and its label ticks it too (`SetHitRectInsets`, documented:
SimpleFrameAPIDocumentation.lua): a black edge was 1.1:1, and only the box took the click. Three kinds:

- **Core**: the dashboard, Race, Prog, Hall of Shame, Statistics, Officers (officers only) and Me, registered by
  `UI.lua`, always on and never listed. A page with columns or cards brings them as its section. Cute starts with
  only these.
- **Built-in**: shipped inside Cute, off until its box in Settings > Modules is ticked: the Guide. Ticking it brings
  its tab and its section at once; unticking takes them and its events away at once.
- **Module addons**: a folder of their own whose toc says `## Dependencies: Cute`, `## X-Cute-Module: 1` and
  `## LoadOnDemand: 1`. The first loading screen of a session finds them in the client's addon list
  (`C_AddOns.GetNumAddOns`, `GetAddOnInfo`, `GetAddOnMetadata`, `GetAddOnDependencies`, `IsAddOnLoadOnDemand`, all in
  Forever's `AddOnsDocumentation.lua`), listed by their toc's title until they register. Ticked, one loads at once with
  `C_AddOns.LoadAddOn` (documented on this client; Blizzard's Camelot code calls it), no reload, and calls
  `Cute:RegisterModule` from its files, the one global Cute makes; ticked in combat, it waits for
  `PLAYER_REGEN_ENABLED` (`InCombatLockdown`, documented), since loading one may make frames, and its box says so.
  Unticked, its tab, section and events go at once, and `C_AddOns.DisableAddOn` turns it off for this character in
  the game's AddOns list, so the next login does not load it, even one that is no LoadOnDemand addon and the game
  would load itself; ticked again, `EnableAddOn` turns it back on first. One the player switched off in the AddOns list
  at character select is the player's word: its box goes unticked at the next login, and only a tick in Settings turns
  it on again (0.6.0's first builds turned it back on and loaded it). The character argument is the GUID, as the
  mainline client's own code passes it (`Blizzard_Minimap/Mainline/AddonCompartment.lua:79`); where that call fails,
  Cute loads only what is on anyway. A module's stats are defined the first time it is on in a session and stay until
  the next login, which its box says when it is unticked.

The choice is per character, in `CuteDB.chars[me].modules` (by id, or by folder for a module addon). Every character
starts with the dashboard alone, a fresh install and one that ran 0.5.x alike, as What's new says at the first login
on 0.6.0 ("Starts with only the statistics; the Guide, switched on in Settings, Modules, ..."). 0.5.x showed every
character the Guide as a fixed tab, and 0.6.0's first builds kept it on for them under that line; the carry-over went
(it was the only path of its kind, and it had already turned the Guide on for 0.4.x's characters by mistake once).
`/cute modules` lists each module, on or off, and opens the section; `/cute guide` (a built-in module's name while it
is off) switches it on for this character, as its box would, and opens its page: a second way to the box. Every check
in Settings is a row button the column's width, its box a visual inside it (UI.lua checkRow), so a click anywhere on
the row ticks it and nothing leans on a hit rect widened over the label (0.6.0 did, and the live client's Modules
boxes took no click).

## The rules and the Guide

`Rules.lua` weighs the seed against what the guild meets in play. A fact's state is `data` (from research only),
`beta` (the beta saw it), `seen` (this guild met it in play), `doubted` (the guild's play contradicts it), `absent` (this
client has no such thing) or `stale` (the whole seed no longer matches the game). The model is
`CuteDB.known.model`: per dungeon, boss, boss's loot item, enchant slot, XP level and faction, its state, how many
members met it, the first time, who (by GUID). It is built again from the seed, Rule 0's verdict, the saved records
and your own counters at every login and three seconds after anything it weighs changes (a burst of records builds
once); the first times and who saw what carry over, so a count never falls as members leave. Beside it,
`CuteDB.known` keeps what only play can tell and no record keeps: the XP samples per level (`xp`), the loot seen per
boss and by whom (`loot`), when members at the doubt level were first seen wearing an item in each slot (`watch`), the
kills a group mate named back (`kills`, rule 9), Rule 0's last verdict (`seed`). The evidence is every member's record
that carries a GUID, the members the officers marked untrusted left out, each member's level the roster's, and a kill
or its level only where rule 9 corroborated it. Learning needs more than one voice (Privacy and trust): no rule
changes the guild's knowledge on one member's word.

**Rule 0, the seed checked against the live client** at login, after the roster and before the Guide draws, fifty ids
a frame: the loot items with `C_Item.GetItemInfoInstant` (nothing back: the client lacks it), the enchant recipes with
`C_Spell.DoesSpellExist`, the factions with `C_Reputation.GetFactionDataByID`, the build with `GetBuildInfo`, each
through `C.Ask` (Core.lua: the answer made plain, and whether the call said anything). A fact the client lacks is
`absent`; a call that throws or gives a secret counts neither way. More than `staleShare` absent (30 %), or another
major version than the seed's, makes the whole seed `stale`: it neither counts as missing nor recommends, and the
Guide says the game differs and runs on the guild's play. A new minor version or build alone is no verdict, since the
share of absent facts is the evidence that the game changed; on any build other than the seed's the beta's facts
count as `data` until the guild sees them. Until Rule 0 is done the seed counts for nothing (the Guide says it is
checking, and how far it got: 150 of 4000). Each ask runs under a pcall of its own, so one id the client chokes on is
recorded under /cute errors and skipped, never the end of the chain; a chain that reaches no verdict all the same (a
frame's callback the client dropped) is closed by a watchdog thirty seconds on, judged on what was asked, and says so
under /cute errors (0.6.0's chain ended on the first swallowed error, "checking" for the rest of the session). A seed that names nothing is none; a partial one is read for what it has. Beside the fixed format the seed
may mark a dungeon whose wings share one instance (`wings`), a boss that is no fight every run meets (`optional`), the
kinds of item each enchant takes (a `list` entry's `kinds`), and name a boss without an encounter id, which is kept by
name and joins as the seed's when the guild kills a boss of that name in that instance. A dungeon may list its quests
(`quests`: a name, QuestBank's id where one joins, the level it opens at, the side), which the Guide shows as they
stand for you; and `awaited` names the dungeons research knows that the client the seed was made from has no map for,
by name and level range alone (no instance id, no bosses). Until an instance id comes for one it is in the model's
`awaited` list, listed by the Guide by its range; an instance whose name is one of them, as the joins compare names
(`R.Norm`, gen_known.py's `norm`: case, punctuation and a leading "The" left out), gives it that id once two members
entered it or a kill a group mate named back was there, and from then on it is the seed's dungeon like the rest (its
range the seed's until kills learn one, its bosses joining as the guild kills them, "Found" under Learned in play).
It takes two, like everything the guild learns, though the seed already names it: one member's entry, or one edited
copy's label and entry, places nothing (the first 0.6.0 build placed it at one). Where two instances carry
the name, the one more members entered is it, so one edited copy naming another instance cannot hold it against the
guild's entries. Its tooltip in the Guide says what places it.

The rules, one function each, their thresholds in `RULES` at the top of the file:

1. **Seen beats believed** (`SeenBeatsBelieved`). A fact a member met is `seen`, with who, how many and when first;
   the Guide says "seen by N members", "seen in the beta" or "from research". Once met, a dungeon or boss is shown by
   the name this game gives it (the discoveries' label); the seed's name, where it differs, is in its tooltip.
2. **New things join** (`NewThingsJoin`). A dungeon or raid entered, or a boss killed, that the seed lacks is added as
   seen, the boss under the instance it was killed in (a world boss under none): a boss once a corroborated kill names
   it, a dungeon once two members entered it or a corroborated kill was there.
3. **Level ranges learn** (`LevelRangesLearn`). A dungeon's range is the `rangeLow` to `rangeHigh` percentile (10th to
   90th) of the levels members had at their first kill of one of its bosses (`k<encounterID>`, each member once), once
   `rangeMembers` (5, two at least) distinct members have; until then the seed's range stands, and with no usable seed
   the levels seen so far, said as such, once two members have them. The percentiles set the tails aside, each rounded half up: five members at 10 % set one
   level aside at either end, so one member boosted through at 12 or farming it at 60 never stretches the range.
4. **Doubt, never delete** (`DoubtNeverDelete`, `SlotDoubted`). A seeded boss the guild's full runs never met is
   doubted, shown dim, "not seen in 3 runs". A full run is a member who killed every boss there the guild has seen,
   once it has seen two or more: while it has met only one, every member who killed that one would pass for a full run
   and doubt the rest (the first 0.5.0 build did), so nothing is doubted. The seed's order of the bosses, which says
   nothing of the paths through a dungeon, is not asked. One boss missing from
   `doubtRuns` (3) such runs is doubted; each more boss missing takes as many runs again, so three runs of Blackrock
   Depths to the Emperor that spare Moira and skip the Grim Guzzler, nine of its twenty-one missing, doubt none. Never
   in a dungeon the seed marks as wings, nor a boss it marks optional. A seeded enchant slot nobody has an enchant in
   `enchantDoubtDays` (14) after a member at `enchantDoubtLevel` (30) or more was first seen wearing an item there
   (your own gear; a member's empty slots) is doubted and stops counting as missing.
5. **Enchant slots** (`SeedEnchantable`, `SeedSlotState`, `SlotState`, `SlotEnchants`). A slot counts on a kind of
   item when a member has an enchant there on that kind, or, for a character at `enchantDoubtLevel` (30) or more, when
   the seed has one for it (on that kind where it names kinds); Missing enchants is the worn slots that count, not
   enchanted. What the guild learns only widens the seed, never narrows it: the seed's own word on a slot
   (`SeedSlotState`: data or beta, else stale, absent or doubted) is kept apart from what the guild has seen there
   (`SlotState`, seen once any member has an enchant there), so one member's enchanted leather bracer leaves the seed
   counting a cloth one, and the seed refuses a slot only stale, absent or doubted. Each enchant the seed lists starts
   from that word and is seen only once that enchant was; an unseen kind's tooltip gives the seed's confidence. (The
   first 0.5.0 build made the whole slot seen at the first enchant on any kind: every other kind there stopped
   counting, and every enchant read "seen on 0 members".) The enchants offered for a
   worn item are the ones that take its kind: where the seed names an enchant's kinds, those; where it does not, every
   kind the slot takes (every kind of armour in a slot takes the same enchants), but in the hands' slots (main hand,
   off hand, ranged), where a two-hander, a one-hander, a shield and a book take different ones, they are counted and
   not named, so a dagger is never offered a two-hander's enchant nor a shield an off-hand's.
6. **The XP curve learns** (`XPCurveLearns`). Each member sends `UnitXPMax` at the level they are, in the hidden
   `xpmax` stat (`"level:max"`, slow; taken when two reads five seconds apart agree, so a ding read halfway is never
   kept); once `xpAgree` (3, two at least) agree on a level, that value replaces the seed's. With no seed for a level the
   most reported value stands once two agree on it; a level nobody reported is estimated from its neighbours (a straight line between two known levels,
   the last two's step past them), and nothing is estimated from fewer than two. Hours to 60 and the Guide's pace run
   on it.
7. **The level cap** (`LevelCap`). `GetMaxPlayerLevel` and `GetMaxLevelForPlayerExpansion`, the lower that reads ten
   or more (as QuestBank reads them), else the seed's 60; a member past it raises it. Deaths while leveling are deaths
   below it.
8. **Loot learns** (`LootLearns`). The first corpse's loot window opened within a minute of a boss kill, in the same
   instance, that holds an item green or better is that boss's: its items are read (coin, currency and grey or white
   items left out), never looted, told in the labels message and kept with who saw it; an item is the boss's loot
   (seen) once two members saw it drop (your own window one of them). A member's loot is taken only for a boss the
   guild has a name for (the seed's included) or a kill a group mate named back, forty items a boss, twenty-four of them
   brought by one member alone (your own window's always kept; where the boss is full, an item from your window or from
   a member holding fewer takes the place of the oldest one of the member holding the most), six hundred bosses from the
   channel and two hundred first from one member, so neither one edited copy's junk nor one member's world greens keep
   anybody's loot out. A container opened
   from the bags (`LOOT_OPENED`'s `isFromItem`) is no corpse, and a trash corpse of greys looted first leaves the
   boss's window to come. No documented call names the corpse a window belongs to, so an add's or a trash mob's corpse
   with a green on it, looted before the boss's, still passes for the boss's. Seeded loot not seen stays `data`; once
   the guild has killed the boss `lootDoubtKills` (5) times the tooltip says it has not been seen in that many kills.
9. **Kills need a witness** (`Claim`, `Corroborated`, `Killed`). A boss kill counts toward rules 1 to 4 only where
   another member in the same group reported the same encounter within a minute. At its kill every Cute claims it with
   the GUIDs of its group and the server's time (`GetServerTime`, documented): `1K|<encounter>@<time>:<group>`, the time
   in base 36, each group member by the last part of their GUID. The group is your party (UnitGUID of party1-4, which
   in a raid are the others of your five), then the rest of a raid (raid1-40) lowest GUID first, 24 in all, so a claim
   fits one message: a raid of forty named whole was 364 bytes, which the client refuses, and no raid kill was ever
   corroborated. Two of one five always name each other; across a raid the lowest GUIDs are named by everyone. Two claims
   that name each other, a minute apart or less, corroborate both kills, kept by encounter and GUID
   (`CuteDB.known.kills`). A kill alone, or in a group with nobody else running Cute, teaches nothing (it counts on the
   Statistics page all the same); a claim naming a member who never names the claimant back teaches nothing. Each
   character keeps its first kill of a boss in a group (`CuteDB.chars[me].claims`) and tells it again with its
   discoveries, at the hello and answering an ask, so a member who was offline weighs it too.

**Officers retune the rules in game.** Every threshold is in Settings > Rules (the Guide's two, its levels near you and
ahead, in the Guide's own section): its label, its value apart from it and right-aligned against a step down and up (a
narrow window cuts the label, never the number), white once an officer set it, the buttons' tooltip saying what it
does, its default and who set it; greyed for members. The values travel with the visibility policy (`1P`, `r_<name>=<value>:<GUID of who set it>` beside the
`id=a` parts, each with when it was set, `@<base 36>`, and `-` for one put back to its default; a 0.4.0 client passes
them by) and apply from an officer, rule by rule: the newest of each wins, so an officer who was away and changes
something before another officer's word reaches their client undoes none of that officer's rules. A value outside its
bounds here is the default again; the members it takes to learn a range or to agree on XP are two at least (a 0.5.0
officer's one is dropped, the default back). A change goes to the guild on its own, three seconds after the last of a
run of clicks; Broadcast now sends them again; "Rules to defaults" puts them back. `/cute rules` prints them.

**The Guide** (a built-in module, off on a fresh install: Settings > Modules puts its tab after Race; `/cute guide`
switches it on for this character while it is off, and opens it) answers one question, what should you do next and with whom.
The band, which stays in view, holds two lines, each with its tooltip:

- **The next best thing**, the rules' pick from the dungeons in range at your level: "Run The Deadmines: 3 guild mates
  online in range, 7 bosses you have not killed, 5 quests". A dungeon fits when it leaves you something to do (a boss
  you have not killed, a quest open to you, or, where no boss is known yet, a dungeon you have not been in); of those
  the one with the most guild mates online in range wins, then the one with the most left for you, then the one
  closing soonest. The tooltip says so and gives every dungeon in range with its counts. When nothing fits it says so
  plainly: "No dungeon known for level 14 yet; The Deadmines opens at 18.", "Nothing left for you in range at level
  20; Blackfathom Deeps opens at 24.", or that it is still checking the research. Officers get the guild's version
  instead: "Most members are 18-23: The Deadmines", the window of twice `guideWindow` levels holding the most members
  by the guild roster's levels (the server's word), and the dungeon whose range holds the most of them; the tooltip
  has the counts. An officer's own pick is still marked on its card.
- Where the knowledge comes from: research checked against this client, research this game no longer matches,
  nothing shipped, or still checking; the build and date (and a build the beta's facts count as research on) in its
  tooltip.

Under it one virtual list (`UI:List`), every row one height, headings included:

- **Dungeon cards**, one per dungeon in range, the next best one marked: the name; a level bar, the range drawn on a
  track against your level (green where your level is in it, grey above you, dim below; every bar on the page on one
  scale), the range in numbers beside it; how sure we are in one word (seen, beta, research, doubted). Under the name
  the bosses as pips (killed white, not killed grey, doubted dim; how many are left on the right; each with your kills
  and how sure in the tooltip); the quests the research knows for it as they stand for you: your side's (the other
  side's left out, `UnitFactionGroup`), done and in your log asked of the client by id
  (`C_QuestLog.IsQuestFlaggedCompleted`, `GetLogIndexForQuestID`), one opening above your level said so, one the
  catalog gave no id named but never counted (the client cannot be asked whether it was done), none from a stale
  seed; and the guild mates online in range, within `guideWindow` (3) levels of yours, nearest first, their names in
  their class's colour beside their level and an Invite button each: four, then "and N more online in range", a click
  showing the rest. The invite is the game's own, `C_PartyInfo.InviteUnit` (documented, PartyInfoDocumentation.lua;
  Blizzard's guild roster calls it with a member's name), sent to the sender string the member's Cute speaks under
  (the name the game takes for a whisper), else the roster's name where it is a plain one; a Kstring is no name to
  send to, and that button says to invite them from the guild roster. Never in combat (`InCombatLockdown`: greyed,
  and a press invites nobody; combat starting and ending draws the page again), greyed where the client says you
  cannot invite (`C_PartyInfo.CanInvite`), "Invited" for a minute after; a mate in your group says so instead. No chat
  line is sent and the chat box never opens.
- **Gear and pace** as compact strips, a row each, their detail in the tooltips. Gear: your Missing enchants, a row a
  slot with the guild's word on it, the enchants Forever has for that slot and the kind of item worn there in its
  tooltip (the seed's, absent ones left out, the ones the guild has on an item first). Under the enchant level, the
  worn slots the seed has enchants for, as one row of advice ("Could take one: Wrist"). Where no slot is known to take
  an enchant at all (no seed, or a stale one, and nothing enchanted in the guild yet) the row says so, "No enchant
  slots known yet: they are learned as the guild enchants", rather than that every worn item has one. Pace: hours to
  the next level and to the cap, at your pace and at the median of the members' paces you may see.
- **Next up**, a short timeline of the dungeons opening within `guideAhead` (5) levels above yours: the level each
  opens at, a dot on a rail, its name, its bar and its word; the seed's awaited dungeons among them by their range.
- **For officers**: one line per dungeon the guild is in range of or has met, with its bar, its members in range and
  how many of its bosses the guild has killed (every boss in its tooltip, with how many members were seen killing it),
  the rest counted on one line; and Learned in play, what the guild's play changed from the research (new dungeons and
  bosses, a dungeon research named without an instance id found, new enchant slots, learned ranges, doubted bosses and
  slots, corrected XP, absent facts, a stale or missing seed). With no research to weigh the play against (none
  shipped, or a stale seed) nothing there is called a change from it: it is what the guild learned, each dungeon or
  raid it met once with its bosses counted on the line and named in the tooltip, the ranges it learned, the enchant
  slots it found.

With a stale seed or none, every section runs on the guild's play and its heading says so: a stale seed's bosses
nobody has met are neither left to kill, nor counted on the officers' line, nor in a tooltip, and its quests are not
shown. A dungeon's, boss's or slot's tooltip has the rest: the range's source, every boss with your kills and how sure,
the loot seen and not. A row with nothing to its right takes the row's whole width, and a note's tooltip holds its
whole text, which a narrow window cuts. Your group, your quests and combat draw the open page again (the module's
events: `GROUP_ROSTER_UPDATE`, `QUEST_ACCEPTED`, `QUEST_TURNED_IN`, `PLAYER_REGEN_DISABLED` and `_ENABLED`, all in
Forever's generated docs), at most once a second. When the leveling module (QuestBank's Quests, the first module to
come over) is on, its best places for your level are meant to join the same pick; it is not here yet.

## Versions: a newer Cute, what is new

Every Cute sends its version (`addon_ver`, in the full record). One newer than yours, compared number by number
(`C.VersionNewer`: 0.5.10 is newer than 0.5.9, 0.6 is 0.6.0), says so in chat once a session, "Cute 0.6.1 is out (you
have 0.6.0): foreverrank.com/addons/cute", and the window's status line says "update available" until you update.
An older or equal version says nothing; anything but two to four dotted numbers (`C.ParseVersion`: "0.5.0-beta",
"0..5", a bare "5") is ignored. The versions come as members' records arrive (`Roster:Apply`) and from the saved
records at login, once the roster is known, each only from a record whose GUID the roster lists and the officers have
not marked untrusted: a copy's made-up version, once marked, announces nothing again. A /reload is the same session: the saved variables remember the chat line (`CuteDB.toldNewer`)
until the next login, which says it again while it holds.

The first login on a version prints its changelog line once, ten seconds on, after the login's own lines: "Cute
0.6.0: Starts with only the statistics...". The line is the page's: `build.py` writes `Cute/Changes.lua` (`C.CHANGES = {
["0.6.0"] = "...", ... }`) from every `<li><b>X.Y.Z</b>...</li>` of the changelog in `addons/cute/index.html`, its
markup taken out and its entities read, ASCII with UTF-8 as decimal escapes, before it zips, and stops when the toc's
version has no entry. `CuteDB.toldChanges` keeps the version told; a version Changes.lua has no line for says
nothing. A first run (saved variables empty) says hello instead, "welcome to the guild's dashboard: /cute opens it,
/cute help lists the rest.", and counts this version as told: what changed in a version nobody ran is no news.

`/cute` opens the window; `/cute` and a page's name (a module's id or title: race, prog, shame or hall of shame,
statistics, officers, me, and guide or a module addon's while it is on) opens that page, a built-in module that is off
(the Guide) goes on for this character first and says so, a module addon that is off says where it is switched on and
opens Settings there, an officer's page asked for by a member and a word that is no page
or command say so; `/cute settings` (or options) opens Settings, `/cute modules` lists the modules, on or off, and opens Settings there; `/cute resend`, `/cute errors`,
`/cute api`, `/cute diag` and `/cute rules` as above; `/cute help` lists them.

## Ship

```
python3 tools/cute/build.py
```

One command, nothing typed by hand: it writes the seed (`Cute/Known.lua` from `gen_known.py`, see The seed) and runs
the seed's `--selftest`, the build stopping with the problems when either fails, writes `Cute/Changes.lua` from the
page's changelog (Versions; the build stops when the toc's version has no line there), zips the addon (the same
`zip -rq ... Cute -x "*.DS_Store"` as before; `--no-zip` keeps the zip you have), regenerates `addons/cute/stats.js`

## The seed

```
python3 tools/cute/gen_known.py             # write Cute/Known.lua when a fact changed, print the counts
python3 tools/cute/gen_known.py --selftest  # check the joins and the file; writes nothing
```

`Cute/Known.lua` is what research and the beta say Forever has, for the addon to start from and throw away where the
game turns out different. It is generated, never edited by hand, from the newest Forever build under `research/wago`
that has every table it reads, and rewritten (and dated) only when a fact changes. Every fact carries `conf`: `beta`
when the beta showed it (a level range starting at 30 or below, with players' records), `data` when only research or
the client's own tables say so. Its header names the build, the sources, the counts and what it leaves out.

- Dungeons, keyed by instance id (`GetInstanceInfo`'s eighth return): `codex/loot.json`'s dungeons joined to the
  client's Map table by name, else by the map the client's encounter table puts their bosses in (The Stockade and the
  Temple of Atal'Hakkar go by other names there; LFGDungeons names no map in this client). Wings that share an
  instance are one entry, as the game reports them: Scarlet Monastery, Dire Maul and Blackrock Spire, each over its
  wings' whole range, its wings named in its `wings` field, which Rule 4 reads (a run is one wing, so no boss there is
  doubted). A dungeon the client has no map for yet (`AWAITED`: The Drowned City, Krol'dok Stronghold,
  Alcaz Prison, Blackmaw Hold, Shaper's Terrace) cannot be keyed: it is seeded in `awaited` by its name and
  loot.json's level range alone, `data`, no instance id and no bosses, so the Guide lists it in Next up; an instance
  of that name two members entered gives it its id (The rules and the Guide). Any other dungeon that does not
  join stops the run with its name.
- Quests, per dungeon (its wings' together): loot.json's, each with QuestBank's id where its title joins one in the
  catalog (`tools/questbank/QuestBank/Data.lua`'s `D.Q` and `D.QN`, titles compared as the joins compare names;
  several of one title narrowed by side, quest level, required level, the catalog's dungeon flag and its Forever
  flags in turn), the level it opens at and the side it is for (the catalog's where loot.json gives none). Their
  confidence is their dungeon's. Today 174 quests, 152 with an id; the summary names the titles several ids or none
  fit, which the Guide names and never counts.
- Bosses, each a fight of the client's encounter table, since the addon reads bosses by encounter id. loot.json's
  bosses join `DungeonEncounter` by name within the instance at a dungeon's difficulties (0 and 1; the same names also
  sit under the Season of Discovery raids' 198, 201 and 215, which players' records never name), a fight of several
  (`Ring of Law: Grizzle`) to its encounter, a near name (Kirtonos the Herald, Gelihast) where only one encounter
  fits, and otherwise through `ALIAS`, each entry with its evidence: Magmatus is Infurnus, Arcanic Enigma Mana
  Elemental, Eric, Baelog and Olaf The Lost Dwarves, Doom'rel, Anger'rel and their chest The Seven, Watchman Doomgrip
  and the Dark Coffer The Vault, the Shade of Hakkar the Avatar, Dathrohan Balnazzar, Gyth Rend. ForeverChanges'
  Guzzler pools the Grim Guzzler's loot (`POOLED`): each item goes to the fight whose boss drops it in the Classic
  database. Encounters loot.json lacks are seeded too. A loot.json boss no fight fits (a rare, a summoned or Scourge
  Invasion boss) is left out, named in a comment under its dungeon. Players' loot records make a fight they ended in
  the beta's range `beta`, and give it the items of a corpse known to be its boss (the game's own creature list, or
  the NPC id Wowhead Forever gives it); a fight linked only by time gives none, since the trash looted after a kill
  is linked the same way (Mana Devourer: seen killed, its loot not told apart yet).
- Enchants per slot: the Enchanting recipes of `codex/recipes.json` not flagged `sod` whose spell enchants an item for
  good and that Forever has: new in Forever, taught by a trainer, or taught by a formula players' uploads or loot.json
  show or the Classic database hands out outside its raids (sold, a quest's reward, dropped by a creature or held in a
  chest that stands outside them, or in a container that is). The formulas only Molten Core and Ahn'Qiraj drop keep
  their eleven recipes out. A spell's slots are its inventory types, else the hands its weapon or shield kinds are
  held in; its kinds are its subclass mask, none listed (any kind) when the mask names every subclass. A spell no item
  in the client passes the game's own test for is left out. Enchant items a Forever source shows obtainable
  (loot.json, players' uploads) are listed in the slots the recipes open and open none of their own: the Mystic Heavy
  Armor Kit (legs, level 30) and the Crude Scope (ranged) wait for a member's item to teach those slots (rule 5); the
  hundreds of others the client carries (arcanums, librams, signets, items named after the recipes) stay out until one
  is seen. Today: neck, chest, feet, wrist, hands, back, main hand and off hand; no head, shoulder or legs, as the
  design says.
- XP to the next level, 1 to 59: QuestBank's `D.TO_NEXT`, `beta` to 30, checked against players' `UnitXPMax` readings.
- Factions: the reputations the quests QuestBank's catalog has met in Forever reward, by CMaNGOS Classic's
  `quest_template` (the client's QuestFactionReward table holds only the amounts), named from the client's Faction
  table, headers left out. Forever's new quests have no reward data there, so the client's other factions with a
  standing (Kirin Tor, Earthen Ring, Theramore Expeditionary Force and the rest) are counted and named in the header,
  for the rules to learn.

`--selftest` builds the seed twice and compares, then checks that every loot.json dungeon is seeded or awaited (and
fails once an awaited one joins, so the list goes when the client gets the map), each awaited one seeded once by its
name and level range with no instance id and no bosses, which LuaJIT reads back; that every quest loot.json lists for
a dungeon is under it and every quest id is the catalog's quest of that title; that every dungeon of wings names
them in its `wings` field, which LuaJIT reads back; that every boss is an encounter of
its instance, none twice, and every `ALIAS`, `POOLED` and `NOT_THAT_FIGHT` entry is still needed and still right; that
no fight ships with no loot beside a left-out boss with loot unless `NOT_THAT_FIGHT` says why that boss is not the
fight; that every instance and encounter players' loot records name is in, `beta` where the beta's range reaches it;
that the neck takes enchants and the head, the shoulder and the legs do not, every slot is opened by a recipe, and no
recipe is in whose formulas drop only in Classic raids; that every spell, enchant, item and faction is in the client's
tables (the login check starts with nothing absent); that the XP agrees with the players' readings; and that the file
is ASCII, loads in LuaJIT, keeps a UTF-8 name whole through its escapes, and is the one this run would write. It
prints the counts per table and confidence, what it joined and left out and why, and ends `problems: 0` and `OK`.
`build.py` runs it after writing the seed and stops on a problem.
